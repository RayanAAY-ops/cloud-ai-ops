# INC-74074c61: Lambda function cloudops-ai-app-dev lacks IAM permissions to access DynamoDB, causing all invocations to fail.

**Severity:** critical

```
cloudops-ai-app-dev-errors at 2026-10-24T19
```

## 💥 Impact

All requests to the Lambda function are failing. The function cannot read from or write to its configured DynamoDB table, blocking all data operations and causing service degradation for downstream consumers.

## 🔍 Root cause

- **95%** IAM execution role missing DynamoDB policy attachment
- **90%** DynamoDB policy was removed or never attached to the role
- **85%** Misconfiguration during deployment or role creation

**Evidence**

- Execution role 'cloudops-ai-app-dev-exec-role' has only AWSLambdaBasicExecutionRole attached
- DynamoDB permission check confirms implicitDeny for all DynamoDB actions (GetItem, PutItem, Query, Scan, UpdateItem, DeleteItem)
- Function configuration shows DYNAMODB_TABLE_NAME environment variable set, indicating DynamoDB dependency
- Empty metrics and logs suggest invocations are failing before completion
- No recent IAM policy changes in CloudTrail

## 🛠 Proposed fix

Attach a DynamoDB policy to the execution role 'arn:aws:iam::523987126142:role/cloudops-ai-app-dev-exec-role'. Add an inline policy or managed policy that grants dynamodb:GetItem, dynamodb:PutItem, dynamodb:Query, dynamodb:Scan, dynamodb:UpdateItem, and dynamodb:DeleteItem permissions on the DynamoDB table specified in the DYNAMODB_TABLE_NAME environment variable (or a wildcard ARN for all DynamoDB tables). This will allow the Lambda function to access DynamoDB and complete invocations successfully.

## ❓ Uncertainty

Without seeing the actual Lambda function code or error logs, I cannot definitively confirm the exact DynamoDB operations performed. However, the permission denial is certain—the role lacks any DynamoDB permissions, which is the blocking issue regardless of which specific operations the code attempts.
